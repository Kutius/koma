# Koma 性能与内存维护指南

> 本文档面向 Koma 的长期维护者与 AI Agent，记录基于 **Go + MyGo（Direct3D 11 原生 GPU UI）** 构建 Windows 轻量化桌面工具时的性能思维框架、观测方法与演进方向，而非具体个案记录。

---

## 1. 核心心智模型：桌面 GPU 应用的四层内存视图

在 Go 编写的原生桌面应用里，“内存占用”不是单一数字。排查或优化前，必须先区分问题发生在哪一层：

1. **Go 堆（Heap）**：业务对象、图像像素缓冲、UI 元素树与每帧临时分配。决定 GC 频率、停顿与峰值内存。
2. **原生用户态内存（Native Heap / DLL Image）**：操作系统组件、字体排版、图形驱动（如 D3D11 用户态驱动与着色器编译器）的私有提交与映像映射。这部分**不会出现在 Go `pprof` 中**，往往决定进程常驻下限。
3. **GPU 显存（Dedicated / Shared VRAM）**：窗口交换链缓冲、离屏模糊/特效目标、上传的位图纹理与字形图集。
4. **OS 工作集（Working Set vs Private Bytes）**：Windows 任务管理器默认展示 **Private Working Set**（当前驻留物理内存的私有页），而提交内存（Private Bytes）包含可被系统安全移入备用列表的闲置页。

**基本原则**：
- 只看 `pprof` 会漏掉驱动与显存；只看任务管理器会混淆“真实泄漏”与“OS 尚未修剪的闲置页”。
- **先分层定性，再动手优化**，避免在占比 <1% 的层级做过度设计。

## 2. 观测与验证方法论

性能优化必须“先量后改、改后复测”，按排查层级组合工具：

- **帧级开销与 GC 压力**：使用 MyGo 内置的 `MYGO_FRAME_STATS` 观测单帧 `build / layout / paint / present` 耗时、每帧分配量、文本排版次数与 GC Assist，必要时配合 `MYGO_GPU=0` 隔离 GPU 驱动基线。
- **Go 堆分配与留存**：通过无头 `ui.Tester` 配合 `go test -memprofile` 与 `go tool pprof -diff_base` 做前后增量对比，重点关注高频路径的 `alloc_space` 与稳态的 `inuse_space`。
- **真实进程与显存画像**：在桌面会话下采集 `K32GetProcessMemoryInfo`（Private Working Set / Private Bytes）、GPU 进程显存计数器、线程数与句柄数，并分别记录**活跃交互态**与**托盘静置态**两套指标。
- **反回归护栏**：对关键资源的释放路径（文档切离、窗口关闭、缓存淘汰）使用 Go `weak.Pointer` 编写自动化 GC 可达性测试，把“不再持有大对象引用”变成可验证的单元测试不变量。

## 3. 五大长期性能方向

### 3.1 窗口即资源域，区分“视觉隐藏”与“资源释放”

对于托盘常驻型桌面工具，“静置轻盈”与“随叫随到”是核心体验指标：

- **状态与窗口解耦**：把轻量的业务状态（配置、历史索引、编辑文档元数据）与重量级的展示载体（原生窗口、UI 渲染树、GPU 交换链与驱动上下文）彻底分离。
- **按需创建，用完销毁**：隐藏窗口通常不会释放底层 GPU 渲染器、交换链与驱动线程池。只要无可见界面，就应允许窗口真正销毁，让共享 GPU 设备引用计数归零并完整卸载驱动上下文；下次需要展示时借助状态持久化恢复位置与内容。
- **冷启动克制**：后台静默自启路径应保持“最小初始化”，只注册托盘与全局热键，不提前拉起图形子系统。

### 3.2 大位图资源的“单一事实源”与冷热分层

截图与标注工具的内存大头永远是高分辨率像素缓冲（单张 4K RGBA 即超过 30 MB）。管理大图像应遵循冷热分层：

- **冷态压缩、热态解压**：历史记录、贴图背景、暂存到托盘的文档等非实时逐像素修改的数据，应以压缩字节（如 PNG）作为持久化形态，按需解码；仅对当前正在编辑的活跃对象保留未压缩 RGBA。
- **单一事实源，禁止无条件拷贝**：明确像素缓冲的所有权流转（谁创建、谁接管、谁只读）。没有像素级修改时直接复用源图，不在“加载 / 解码 / 缓存 / 导出”链路中层层防御性克隆或重复编码。
- **GPU 纹理生命周期意识**：
  - 同尺寸内容刷新应优先**原地更新纹理**，避免频繁创建新位图身份导致旧纹理在渲染器回收窗口期内堆积显存。
  - 小区域采样（如放大镜、局部预览）绝不为此复制整屏级纹理。
  - 已由压缩数据或源图支撑的位图，在上传至 GPU 后主动释放 CPU 侧像素与缩略层级副本，避免 CPU + GPU 双份常驻。
- **显式预算上限**：内存缓存不能只限“条数”，还要限“总字节数”，防止高分屏下的极端样本撑爆常驻内存。

### 3.3 渲染热路径的帧预算与零抖动纪律

MyGo 的声明式/即时构建视图会在交互与动画期间高频执行，维护 UI 代码时应保持热路径克制：

- **绘制回调零堆分配**：`Draw` 与材质渲染函数会按帧反复调用。高频使用的着色器参数容器、临时切片与几何缓冲应复用或池化；避免在像素循环中触发接口装箱。
- **合并图元，拒绝场景 Op 爆炸**：重复性、大面积的背景纹理或网格（如点阵、棋盘格）应优先用单次 GPU 着色器绘制，避免向场景树与增量 Diff 系统注入数千个细碎绘制指令（同时注意为无 GPU 加速环境保留低开销回退路径）。
- **高频手势与重计算解耦**：指针移动、拖拽、缩放等 60–120Hz 事件中只更新轻量坐标与轻量矢量预览；耗时的 CPU 像素裁剪、模糊与重编码尽量推迟到交互定型（如松手）或后台异步阶段。

### 3.4 原生 FFI 边界与 OS 回收节奏

纯 Go 调用 Windows API 省去了 CGO 成本，但原生系统边界仍有隐性开销：

- **原生句柄与回调有界化**：系统回调 thunk（如 Windows 回调注册）在运行时中可能永久占用有限槽位，必须作为静态单例初始化复用，绝不可在高频业务调用中动态创建；GDI / DWM / 文件句柄必须严格作用域配对释放。
- **回收时机与静置态对齐**：内存回收（GC、`FreeOSMemory`、OS 工作集修剪）应做防抖合并，且**只在确认进入无窗口静置态后执行**——既避免活跃交互期因强行换出物理页引入软缺页卡顿，又能让闲置常驻进程把物理内存及时交还给操作系统。

### 3.5 最小构建面与依赖克制

性能同样包含启动速度、磁盘体积与内存映像大小：

- **裁剪未使用的平台子系统**：纯原生 UI 应用应在构建阶段剔除不需要的运行时模块（例如 WebView 相关胶水与符号），同步降低二进制体积、进程映像映射开销与冷启动路径长度。
- **审慎引入常驻能力**：新增功能前先评估其对“托盘静置内存 / 首次唤起延迟 / 峰值显存”三项指标的影响，不让低频特性污染高频路径的常驻成本。

## 4. 变更自检清单

涉及窗口生命周期、图像处理、渲染着色器或系统调用的改动，合入前建议按顺序自检：

1. **边界**：是否新增了动态系统回调、未配对原生句柄或脱离窗口生命周期的全局引用？
2. **拷贝**：大图像路径是否存在重复解码、重复编码、无条件 `Clone` 或新建重复 GPU 纹理？
3. **热路径**：视图构建与 `Draw` 回调在无状态变化或高频鼠标移动时是否产生明显堆分配或大量 Op？
4. **静置态**：关闭所有可见界面后，GPU 显存与驱动线程是否归零，Private Working Set 是否回落至预期区间？
5. **护栏**：是否为新增的资源缓存或释放路径补齐了自动化可达性/边界回归测试？
